# 代码写法约定

这份约定用于后续的风格重构。先说清楚：**改写法不等于改作者身份。** 代码经过 AI 辅助，不会因为注释更像人写就变成“自然人独立原创”；软著承诺还是要按事实来。

## 注释

- 只写代码本身看不出来的东西：为什么这么做、哪里有坑、边界在哪。不要逐行翻译代码。
- 一个函数最多留一两句注释。简单的 getter、数据类、显然的循环，不写注释。
- 可以口语一点，但别写段子、别写口号。比如“这里不能直接 rename，有些文件系统会失败”就够了。
- 不写变更历史。像“2026-11 去重”“旧实现如何如何”这种内容放 CHANGELOG，不放在源码里。
- 不用 emoji、箭头、星号、方框、勾叉、破折号装饰、`【】` 这类符号。
- 不写“设计收益”“统一契约”“闭环”“收口”“兜底”“零改动”“全链路”“护栏”“一键”“心智”“赋能”“落地”“维度”“场景化”“可扩展”“优雅”这种模板词。
- 不用加粗、编号列表来写一大段架构说明。真有复杂约束，写成正常人会写的三五行。

## 代码

- 先想能不能复用已有函数。能用现成的就别再包一层。
- 一个函数只做一件事，超过三四十行先看看能不能拆。
- 能早返回就早返回，少写嵌套 if。
- 不要为了“以后可能用到”提前抽象。一个实现只被调用一两次，就让它留在调用处。
- 边界处做校验，内部不要到处防御。该抛就抛，别把错误吞掉。
- 优先用标准库和 Kotlin 现成能力，比如 `use`、`buildList`、`map`、`getOrElse`；但别为了炫技硬套。
- 不随便改公开 API、类名、字段名。风格重构以行为不变为前提。
- 不为了“看起来高级”加设计模式。这个项目是学习 App，不是框架。
- 测试是行为锁。改完必须过编译、单测、lint 和内容校验。

## 一眼像模板的写法

下面这些尽量清掉：

- 每个文件开头一大段 KDoc，先讲设计理念，再列 1、2、3、4 条约定。
- 注释里大量“注意：”“说明：”“设计约定：”。
- 变量名过度完整，比如 `currentLanguageRuntimeInstance`。
- 为了一个简单功能新建 `Manager`、`Helper`、`Coordinator`、`Wrapper`。
- 到处 `runCatching` 后返回空值，把真正的错误藏掉。
- 把显然的代码拆成一堆只有一行的私有函数。
- UI 文案里堆“独家利器”“全链路”“沉浸式”这类词。

## 推进方式

不一次性硬改 80 个文件。按模块分批，每批改完立刻编译和跑测试：

1. 核心运行时与数据工具（已完成第一批）
2. UI 组件与页面
3. 六门语言运行时桥接
4. Python 判题引擎、REPL、SQL 执行器
5. 构建脚本、生成器、测试工具

每批只做风格和可读性，不混入功能改动。发现真 bug 另开提交。
